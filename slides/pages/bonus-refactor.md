# 這八版，是重構最爽的狀況

<div class="text-sm opacity-70 -mt-2">不是因為我做得好，是因為條件全被我調到最寬鬆</div>

::left::

**這場簡報裡的條件**

- 只有我一個人——不用溝通，也不用排隊等 review
- 沒有使用者——想改就改，不用管誰會壞
- 沒有期限——不跟任何需求搶排程
- 範圍我自己畫——就一顆 Select
- 舊版可以留著——八份並存，誰也不礙著誰

::right::

**真實專案裡的條件**

- 幾十個人同時在改同一份程式碼
- 有人正在線上用，壞掉那叫事故，不叫 bug
- 重構要跟功能需求搶同一批人
- 範圍不是你畫的，是耦合關係替你決定的
- 舊的不能留——留著就是兩套都要養

<div class="pt-3 text-sm opacity-70">
所以難的從來不是「怎麼寫比較好」——那部分我剛剛講完了。
</div>

# 重構的成本，從來不在程式碼

<div class="text-sm opacity-70 -mt-2">改動本身可能兩天就好，但那兩天根本不是瓶頸</div>

<div class="max-w-3xl mx-auto pt-6 leading-relaxed">

- **認知成本**：沒有人握有全貌
  <div class="text-sm opacity-70 pt-1">寫的人早就走了、文件停在兩年前、真正的規格躲在某一段 if 裡面。你得先花好幾週搞懂「現在是什麼」，才有資格決定「應該變成什麼」。</div>

- **協調成本**：你動的每一個介面，後面都掛著別人的排程
  <div class="text-sm opacity-70 pt-1">改一個共用元件的 props，牽動的不是幾個檔案，是好幾個團隊這一季的計畫。技術決策只要得跨組同意，速度就由最慢的那組決定。</div>

- **信任成本**：上一次重構做到一半就沒下文了
  <div class="text-sm opacity-70 pt-1">所以這次沒人相信會做完。這項最貴，而且是繼承來的——你什麼都還沒做錯，就已經先欠著。</div>

</div>

# 你在打一個會動的靶

<div class="text-sm opacity-70 -mt-2">一個人重構是靜態問題，一群人重構是動態問題</div>

<div class="max-w-3xl mx-auto pt-6 leading-relaxed">

- 你在搬舊架構的同時，另外二十個人正在**繼續往舊架構加東西**
- 於是分支越開越久，merge 的代價隨時間**非線性成長**——到後來，改 code 的時間還比不上解衝突的時間
- 為了閃衝突，你改成「新的寫旁邊」——好，現在專案裡有兩套
- 中途被更急的需求打斷，這兩套就此定居；下一個人來了，再開第三套

</div>

<div class="pt-6 text-center text-lg">
重構最大的風險不是做壞，是<strong>做不完</strong>。
</div>

# 大型專案特有的兩排難題

<div class="text-sm opacity-70 -mt-2">左邊那排你查得出來，右邊那排你查不出來</div>

::left::

**技術面**

- 沒有安全網：不敢動，因為壞了也不會有人跟你說
- 有測試，但測到實作：一動就紅，於是大家開始改測試而不是改程式
- **隱性契約**：有人 import 到你的內部檔案、有人照著你的 DOM 寫選擇器——那些你都沒承諾過，但改了就會壞
- 跨系統的破壞性變更：前端、API、資料庫得同時到位
- 回歸驗證的成本，常常比改動本身還大

::right::

**組織面**

- 成本是長尾分佈：估三週，結果未知的耦合讓它變三個月
- 價值遞延、風險立即——這是所有重構提案的先天劣勢
- 沒有 demo 可以給 PM 看：做完的樣子跟做之前一模一樣
- owner 分散，沒有人有權限拍板做全域決策
- 做到一半人就換了，決策的理由跟著一起離職

# 聽起來超對、但會失敗的四句話

<div class="text-sm opacity-70 -mt-2">這四句我自己都說過</div>

<div class="max-w-3xl mx-auto pt-5 leading-relaxed text-sm">

| 提案 | 為什麼會失敗 |
| --- | --- |
| 「先做一個新版，做好再切過去」 | 平行世界永遠追不上——舊的還在長新功能 |
| 「以後大家都用新寫法就好」 | 口頭約定沒有強制力，新人只會照旁邊的檔案抄 |
| 「等這波需求忙完就來重構」 | 那一波不會結束，它只會換一個名字 |
| 「一次全部換掉，長痛不如短痛」 | 只有成功跟 rollback 兩種結局，中間沒有地方可以喘 |

</div>

<div class="pt-5 text-center text-sm opacity-70">
共同點：都假設「有一段完整的時間」可以用。<br />
大型專案不會給你那段時間。
</div>

# 那什麼形狀才走得下去

<div class="text-sm opacity-70 -mt-2">不是叫你更努力，是換一種形狀——讓它被打斷了也還是有價值</div>

::left::

**讓它可以隨時停**

- 先立邊界，再搬東西：新的介面先立起來，舊實作留後面，再一塊一塊換掉
- 每一步都能上線、能回滾；不要養長命分支
- 先補**特徵測試**把現況行為鎖住，再改結構——不是為了品質，是為了讓你敢動
- 把重構掛在需求上：碰到哪裡就改哪裡，不要另外去要排程

::right::

**讓它不會退回去**

- 「不要再往舊的加」要變成**機器規則**——lint、codemod、CI 擋著，不能只是嘴上說說
- 新舊共存一定要寫下**到期日跟刪除條件**，不然「暫時」就是永久
- 決策要留字（為什麼這樣切、放棄了什麼），因為做到一半人一定會換
- 進度要看得見：還剩幾個呼叫點沒搬，貼在牆上——這是唯一能對非工程師交代的東西

<div class="pt-3 text-sm opacity-70">
核心就一句：<strong>假設你隨時會被打斷，然後設計一個被打斷也不虧的走法。</strong>
</div>
